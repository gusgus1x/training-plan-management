feat(employee): carry the durable user key alongside employee_id

employee_id is a surrogate that a re-import of employee data can reassign, and
every training record hangs off it. employee.user_id - the HR source system's
UserID, which never changes - has existed since migration 25 but only scripts
ever read it. This starts moving the application onto it.

Both keys now run in parallel. Nothing is dropped, the UI still sends the old
one, and every step is reversible.

Migration 27 makes employee.user_id NOT NULL and replaces its filtered unique
index with a plain one, now that the mock employees without a UserID are gone.
It re-checks for nulls, blanks and duplicates itself and throws rather than
half-applying, instead of trusting the check that was run when it was written.

Migration 28 gives the five child tables an employee_user_id, backfills it,
verifies every row agrees with the old key, and only then adds the foreign
keys. It is named employee_user_id because user_account already has a user_id
of its own.

NOT NULL immediately surfaced that the app never supplied a user_id when
creating an employee - the field parked as optional in Phase 9. It is required
now, wired from the form through validation to the repository. It deliberately
does not fall back to employee_code: that value gets rewritten by source syncs,
which is the whole reason user_id exists.

Authorization moved in one piece rather than a half-step at a time. The
principal carries employeeUserId, and both ownership checks accept either key
while proving nothing for an account that carries neither - the state every
account is in today, since user_account.employee_id is deliberately still NULL.
Tests pin both cases.

The API takes the durable key only when the caller names it. Every user_id in
the database is an 8-digit number, so inferring the key from its shape would
rest on employee_id never reaching 8 digits - a silent assumption on the
identifier that decides who may act on whose record.

Also fixes the test suite it ran against: nine gated suites loaded only
.env.local, which this project does not use, so they could never reach a
database at all; and two suites wrote to the live server with no gate.
